# Phase 5 conversation-quality audit, 2026-10-07

Requested review of latest logs, repetition, stopping/concluding and immediate-help requests. Application runtime code was not changed in this audit. No new live model calls or paid usage. Latest saved test outputs, current frontend/backend contracts and two synthetic offline probes were inspected.

## Findings

1. **Confirmed fallback repetition and irrelevant questions.** `conversation_service.question` adds a money-loss question to general incidents without requiring a financial signal. On follow-up timeout/rejection, `submit` calls this selector regardless of whether the citizen asked for explanation/help/summary. The question remains unknown, so it can be selected again. Offline probe: Instagram harassment → "Why are you asking about money?" → "Enough questions. Tell me what to do now." → "Please summarize and conclude…" all produced the same money-loss question. Appropriate preservation/platform/reporting actions already existed in the backend.
2. **Confirmed citizen control is provider-dependent.** Intent schema has pause/question/etc., but no explicit plan/summary/conclusion intent. Existing pause handling works when correctly extracted; if understanding fails, explicit "Stop asking questions. Give me the plan." still generated the money-loss question in the offline probe. A model failure must not undo the citizen's clear request to pause.
3. **Confirmed action presentation is disconnected from the request.** Backend approved actions can exist while the chat continues questioning. AI prompt prohibits procedural action prose; one explanation move references one action. Most nonurgent actions sit behind initial UI understanding review. Typed "what should I do?" does not trigger the button's structured `case_review` path. Need a validated response/presentation contract using existing approved actions and concise known-fact review, preserving early urgent help and unknowns.
4. **Confirmed model/validator mismatch plus provider failures.** Latest account run rejected a proposed follow-up with `QUESTION_FIELD_MISMATCH`, then process explanation referred to checking money loss. Latest comprehensive run: financial explanation timed out; threat response rejected with `ACTION_IN_INVESTIGATION`; natural financial receipt review succeeded. Some earlier failures were fixed (helpline numeric grounding, schema reply cardinality); current evidence does not support blaming all remaining failures on quota/timeouts. Exact rejected account/threat prose was not preserved per turn, so its semantic validity cannot be established from the rejection code alone. Current regex field/action validation is a candidate cause of false rejection, not proof that every rejection is wrong.
5. **Untested urgent witness/incident-switch behavior.** "Someone just got harassed in front of me; what should I do?" was not in the saved live journeys. Existing immediate-danger fact/policy is useful, but no explicit witness/affected-person relationship or validated new-incident scope exists. Must distinguish physical/online context and who is affected; avoid silently adding another person's incident to an existing financial case. Do not infer immediate physical danger from harassment alone. Present applicable reviewed urgent actions before routine reporting questions; one consequential safety clarification can be appropriate. Any new bystander-specific critical instructions require reviewed policy/source support, not model invention.
6. **Acceptance coverage gap.** Latest three-route live harness mainly uses an opening story, "Why are you asking?", attachments and reload; language regressions are only two turns each. These prove useful stages but not natural completion or extended conversation. Historical unit coverage does not replace live multi-turn review of answer usefulness, repetition and effort. Missing acceptance chains: repeated nonanswers, explicit stop/plan/summary, understanding failure during stop, corrected misunderstandings, distress, witness incident switches and an already adequate story ending with useful next steps.

## Required work order

1. Turn these reproductions into failing behavioral regression tests. Keep diagnostic probe separate from acceptance: its two passing checks reproduce bugs, they do not mean the product passed.
2. Make fallback intent-aware, scoped to known incident signals and question history. Answer/help/wait rather than repeat an unrelated unknown. Persist pending question disposition across reload; allow meaningful reasking only when new facts change its purpose.
3. Persist citizen requests for pause, current plan and summary/conclusion. Define useful sufficient understanding without a universal field-completion checklist or fixed turn limit. Safe behavior must survive provider failure.
4. Connect those requests to deterministic approved actions and minimal understanding review in chat. AI can explain; application renders the exact reviewed instructions and truthful source/status. Do not relax action ownership or let arbitrary AI prose become policy.
5. Audit semantic validation against captured synthetic proposals. Separate actual unsafe output from wording/field mismatches, with grounded safe fallbacks that preserve useful valid content. Test safety negative cases alongside false-rejection fixes.
6. Establish supported witness/emergency boundaries, ownership of facts and incident-switch isolation; add policy only where source review supports it. Run realistic multi-turn live journeys across all initial routes and human-review effort/conclusion, not just JSON/status.
